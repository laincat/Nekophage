为什么这套分层值得保留
  • 漫画源兼容、备份规则和协议只实现一份；平台只承担自身系统能力。
  • Go 桌面直接调用；iOS 通过 gomobile，牺牲少量 JSON/base64 拷贝换取同一逻辑。
  • 每源独立运行时与 Cookie 分区降低状态串扰；代价是源越多运行时数量越多。

依赖地图

版本来自当前 go.mod / Package.swift。没有凭空升级依赖，也没有把安装工具当作产品运行依赖。

所属库 / 框架版本职责与代价
SQLite 实际用于读取官方备份数据库；即使业务数据主要保存在 JSON 文件，它仍是 Core 的运行依赖。Core 链入客户端时会带来体积成本，不能简单删除。

先清理能证明的问题

优先级按影响排序。已修复表示本地源码已改并有针对性验证；不自动等于发布、iOS 真机通过或真实账号通过。

最该优化的不是语言，而是资源边界

01 / IMAGE

图片内存

iOS 已有 ImageIO 降采样与 NSCache 的 128 MiB 成本上限。桌面已按条数设上限并淘汰最旧条目；条目大小差异大，按字节预算与并发限流是下一步。

02 / LIFETIME

任务生命周期

取消 ID 竞态已修，桌面过期回包已按票据丢弃。下一步是让被替代的请求真正取消，而不只是让结果不被采用。

03 / BRIDGE

跨语言拷贝

iOS 的正文需 Data → base64 → JSON → Go。优先打通真流式，之后再用测量决定是否换更低拷贝接口。

复杂度集中点

这里只统计规模与结构，不虚构启动时间、吞吐量、峰值内存或优化百分比。需要基准测量后才能给量化收益。

下一轮建议顺序

  1. 接入流式网络桥，验证首块早于请求结束、取消实际终止底层任务。
  2. 桌面改为按字节预算、并发限流，并真正取消被替代的请求；按长列表与慢网络测量。
  3. 缩小桌面 app.go 的状态职责，将搜索、浏览、阅读器生命周期拆开。
  4. 桌面已新增真实模块 pin 门禁；iOS 继续补 framework 产物级证据，避免版本戳与链接产物脱节。
